# PoshanEye project facts (verified from repository)

PoshanEye is a child growth and nutrition screening app. Its current screening output is an ML classification for decision support, not a diagnosis and not a WHO certification or validated clinical result. The repository does not establish clinical validation.

## Current prediction path

Flutter's AI scan screen captures one photo and sends it with age, sex, height, weight and optional head circumference, waist and MUAC fields to an authenticated non-persisting preview endpoint. The preview route verifies the selected child, writes a random-name temporary upload, runs `backend/hybrid_predict.py`, returns the result and deletes the image in `finally`. After caregiver confirmation, the app uploads the image again to the authenticated save endpoint, which repeats inference, stores only the screening result and vitals in MongoDB, returns the result, and deletes its temporary image. Screening history is stored in MongoDB; the photo is not included in the saved screening document. A legacy root `/predict` endpoint also remains, is unauthenticated, and now uses a random-name temporary upload with `finally` cleanup. The Flutter scan flow no longer calls it. Deployment logs/storage must still be reviewed separately.

The production predictor uses one submitted image (the API is not a paired front/rear-camera fusion flow). It resizes RGB input to 224x224 and applies MobileNetV2 preprocessing to obtain a 128-value `image_dense` embedding from `models/image_best.h5`; it discards that legacy model's four-class softmax head. MediaPipe Holistic extracts 21 face/pose geometry features. DeepLabV3+ with MobileNetV2 backbone predicts a 512x512 upper-arm mask and derives 11 connected-component geometry features; these are normalized against the MediaPipe shoulder span when available. Anthropometry has eight slots: age in months, male indicator, height, weight, head circumference, waist, MUAC and derived BMI.

Production concatenates the feature blocks in this order: image 128 + MediaPipe 21 + segmentation 11 + anthropometry 8 = 168 values. The JSON preprocessor imputes missing/non-finite values using training medians and standardizes using training means and standard deviations. The final model is a class-balanced RBF SVM. A portable representation exists for Flutter offline inference, but the app scan screen's current API submission path uses backend inference. TFLite is used for the image feature extractor, not the final SVM. Missing age/sex/measurements can be median-imputed, so the output can be affected; this is not equivalent to a valid clinical assessment.

The backend returns one of: healthy, underweight, stunted, stunted and underweight. These are the model's dataset labels. In this project the label-generation source is the AnthroVision `multiclass_label` field; the runtime code does not calculate WHO z-scores. It therefore does not implement WHO diagnostic thresholds. Underweight generally refers to low weight for age; stunting to low height/length for age. These terms here explain the label names only and do not mean this model clinically determines the WHO indicators.

## Verified production evaluation

`Poshaneyemn/production/results/report.md` reports the full feature SVM on a frozen child-level test set of 321 children: accuracy 0.6791, macro precision 0.6463, macro recall 0.4671, macro F1 0.4623, weighted F1 0.6899 and balanced accuracy 0.4671. The per-class supports are healthy 225, underweight 53, stunted 9, and stunted-and-underweight 34. Per-class recall respectively is 0.7689, 0.5472, 0.1111 and 0.4412. Multiclass ROC-AUC is not reported in this production report. The very low recall for the stunted class and its support of nine mean the result needs particular caution. These metrics describe this evaluation split, not guaranteed real-world accuracy.

## Nutrition plan implementation

The plan is generated by deterministic Python rules in `backend/services/nutrition_service.py`; it is not generated by Sarvam or another nutrition AI and is not fetched from an external nutrition database. The authenticated endpoint reads one child's screening history from MongoDB. The latest predicted class selects the support focus; previous labels and recorded trends affect follow-up text. Saved age limits texture guidance. Optional region selects a state food list; vegetarian preference and supplied allergy exclusions filter suggestions. The rules create example meal slots and food suggestions, not measured portions, nutrient totals or calorie targets. If age is absent, the plan says age-specific advice is limited. A high concern should be discussed with a qualified health worker or clinician. Do not treat the model classification or generated plan as medical treatment.

## Privacy and scope

The assistant chat endpoint requires an authenticated user and sends the user question plus at most ten conversation messages to Sarvam. It may attach a small server-verified summary only when the app says the parent is on the results or nutrition screen and the question explicitly refers to the current child/result/plan. The backend verifies the authenticated parent owns that child, reads their records server-side, and sends no child name or identifier. It includes only the latest classification, the matching rule-generated plan summary and food suggestions for nutrition questions, and a saved measurement only when that field was asked about. It does not attach images or full history. The optional coarse region is used server-side to rebuild the same regional food rules and is not included in the context sent to Sarvam. Health-worker child context is not enabled because the repository has no selected-child assignment check for assistant requests. Never infer a child's screening result from static knowledge. A user may still include sensitive information in their own spoken question; the chat system cannot guarantee that user-entered content is scrubbed before it reaches the provider.

## Quality and limitations

Correct framing, lighting, unobstructed face/shoulders/arms, pose and camera distance can affect visual feature extraction. The code does not perform an explicit blur-quality gate in the prediction route. Missing or inaccurate anthropometry is imputed or changes the input and can affect predictions. A photograph alone cannot establish nutritional status. The model has limited and imbalanced test support, especially for stunted cases. WHO guidance below is separate from the model's label logic.
